# vp-linux.py: Linux awareness for gdb

`vp-linux.py` lets gdb read a Linux guest's processes and kernel log while the
target is stopped. It also moves the kernel symbols to the running kernel's
KASLR offset.

The script reads everything through the kernel's own DWARF types and names
only fields. It does not use Linux's `scripts/gdb`, which needs a
`constants.py` generated by the kernel build; Ubuntu's debug symbols do not
include that file.

## In VP Studio

VP Studio loads the script by itself in debug sessions of type `gdbtarget`.
The setting `vpStudio.debug.linuxAwareness` controls this and is on by
default. VP Studio adds two `initCommands`, which run right after the attach
while the target is still stopped:

```
python import runpy; runpy.run_path("<extension>/tools/gdb/vp-linux.py")
vp-kaslr -q
```

The first call stack is therefore already right, even with KASLR on.

The **Guest Processes** view (Explorer, visible while such a session runs)
reads `-vp-ps -t` each time the target stops, but only while the view is
open. A read takes about a second of gdb time. The view shows:

- the CPUs, with what each one runs;
- the processes as a tree by parent, with their threads.

**Show Guest Kernel Log** (in the view's title bar) opens the kernel log in an
editor.

With older debug configurations, or with the setting off, the view loads the
script the first time it reads.

## By hand

```
(gdb) file vmlinux
(gdb) target remote :1234
(gdb) source tools/gdb/vp-linux.py
(gdb) vp-kaslr        # only needed with KASLR; vp-ps and vp-dmesg do it too
(gdb) vp-ps -t        # -t: threads too
(gdb) vp-dmesg -n 20  # the last 20 records
```

Tools use the MI commands `-vp-ps [-t]`, `-vp-dmesg [-n N]`, `-vp-kaslr` and
`-vp-linux-version`. They return the same data as MI results. Through the CDT
adapter they are sent as a DAP `evaluate` request: the expression is the
command with a leading `>`, for example `>-vp-ps -t`, and the context is
`repl`. CDT returns the MI result as JSON in `body.result`. These MI commands
need gdb 12 or later.

## How it works

**KASLR.**
- The script first checks whether `kimage_vaddr` reads back as `_text` at the
  addresses in the symbol file. The arm64 kernel sets `kimage_vaddr` to where
  its image runs, so a match means no offset is needed.
- If not, it takes `VBAR_EL1 - vectors` from each CPU as a candidate offset.
  It keeps the candidate for which `kimage_vaddr` checks out, then reloads
  the symbol file with `symbol-file -o`, or `add-symbol-file -o` when the
  kernel was not the main symbol file.

**KPTI.** arm64 turns KPTI on together with KASLR. While a CPU runs user code
(EL0), the kernel is not mapped in its page tables, and gdb reads memory
through the selected CPU's MMU. The script therefore reads through a CPU that
is in the kernel (EL1, for example an idle one). Afterwards it selects the
debugger's own thread again.

**Processes.**
- The process list comes from `init_task.tasks`.
- Threads come from `signal->thread_head`, or `thread_group` on older kernels.
- What each CPU runs comes from the per-CPU `runqueues` (`rq->curr`), at
  `&runqueues + __per_cpu_offset[cpu]`.
- The state letter is worked out the way `ps` does it (R, S, D, I, T, Z, …).
  The script reads `__state`, or `state` before Linux 5.14.

**Kernel log.** The script reads the printk ring buffer of Linux 5.10 and
later (`prb`). It walks the descriptor ring from `tail_id` to `head_id` and
takes committed and finalized records. Text blocks start with their
descriptor id, and a wrapped block is at the start of the data ring.

## Verified

Checked on 2026-11-16 with the Ubuntu 22.04 platform (Linux 5.15, 8 CPUs,
KASLR on, the original `ubuntu.dtb`), through gdb 15.1 and through the CDT
adapter 3.0.0:

| Check | Result |
|---|---|
| KASLR offset | 0x498b99600000, the same as the profiler finds (G-05) |
| Processes | PIDs and names identical to the guest's `ps -e` (140 processes) |
| Kernel log | Identical to the guest's `dmesg`: 389 lines, same md5 |
| What each CPU runs | Two busy `sh` loops shown running on their CPUs; threads such as NetworkManager's `gmain` placed under their process |
| Speed | `-vp-ps -t` about 0.8 to 1.3 s; `-vp-dmesg` about 0.15 s |

## Limits

- Only arm64 is supported for KASLR and KPTI.
- The kernel log needs Linux 5.10 or later.
- If every CPU runs user code at the stop, the kernel cannot be read; stop
  again later.
- While the guest runs, the lists show the last stop.
- Pressing Stop (terminate) on an attach session makes CDT pause the target
  and disconnect, so the simulation stays halted. Disconnect, the default
  button for attach sessions, detaches and the simulation goes on.
